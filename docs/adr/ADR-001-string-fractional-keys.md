# ADR-001: String fractional keys, ties broken by (key, entity_id), interleaving accepted

Status: Accepted (SPEC §3.7, amendments 2–3). Date: 2026-10-16.

## Context

Lists and cards need an order that every replica computes the same way, that allows an
insert between any two neighbours without touching them, and that never loses precision.
v1 used float positions, which run out of precision after about 50 halvings of one gap.

## Decision

- Keys are base62 strings compared as bytes, generated by a **credited port of David
  Greenspan's fractional-indexing algorithm** as implemented in `rocicorp/fractional-indexing`
  (CC0-1.0, public domain; attribution in both `keys` modules). A key is a variable-length
  integer part followed by a fraction that never ends in `0`.
- `keyBetween(a, b)` is deterministic and throws unless `a < b`. Upstream silently swaps
  reversed bounds; we throw so a caller bug cannot pass unnoticed.
- Render order is `(position_key, entity_id)`. No replica suffix in the key.
- Inserting between neighbours that share a key first re-keys the upper neighbour (and every
  further neighbour sharing it) with ordinary `SET_PLACEMENT` ops (`keys.planInsert`).
- A key longer than 40 characters triggers a rebalance: fresh keys written as ordinary
  `SET_PLACEMENT` ops. Validation caps keys at 64 characters.

## Alternatives

- **Floats.** Precision ceiling; rejected in v2.
- **Pure fractional strings (no integer part).** Simpler, and literally "never ends in 0",
  but appending at the end of a list, the most common edit, grows the key by about one
  character every few appends; 2,000 cards would need rebalancing many times over.
- **RGA or another sequence CRDT.** No interleaving and no rebalancing, but a much larger
  surface (tombstoned elements, origin pointers) for a board with tens of cards per list.
- **Random jitter in keys.** Avoids equal keys, but makes `keyBetween` non-deterministic and
  vectors impossible. Kept as a possible Phase 3 client-side mitigation, not core behaviour.

## Consequences

- **Equal keys are common, not rare.** The midpoint is deterministic, so two replicas that
  append to the same list at once pick the same key; ordering then falls to the entity ID.
  Measured over 200 generated fuzz scenarios, the final views held 1,555 adjacent pairs with
  equal keys (one-off stats script over `scenarioArb()`, `fc.sample(..., {seed: 42})`).
- **Known anomaly: interleaving.** Two users inserting several cards into one gap at once
  can see them interleave, and an insert concurrent with a rebalance can land elsewhere
  (vector 046: the insert sorts above both rebalanced cards). Deterministic on every
  replica, so it never breaks convergence; acceptable for a board.
- Appends stay short: 2,000 consecutive appends never exceed 4 characters, and rebalancing
  2,000 entries gives keys of at most 4 characters (asserted in both `keys` test suites).
- The rebalance path only runs when a key exceeds 40 characters, which ordinary random
  scenarios almost never reach (longest key 5 over 200 scenarios). A dedicated fuzz property
  forces same-gap pressure; in 50 sampled scenarios all 50 rebalanced. That property found
  that the generator never rebalanced *list* keys (an `ADD_LIST` key reached 65 characters
  and failed `validateShape`), now fixed.
